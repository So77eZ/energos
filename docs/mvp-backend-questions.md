# MVP: задачи на стыке фронта и бэка

Актуально для `mvp` на коммите `a11bb72` (10.10.2026). Всё отмеченное «проверено»
проверялось запуском стека в docker (бэк + Postgres + Caddy + фронт), а не чтением кода.

Фронт работает с API ветки `mvp` (`docs/api.md`, `backend/api/v1/*`). Где API не хватает,
он обходится адаптером или прячет фичу за флагом (`frontend/src/shared/config/features.ts`).
Ниже — что осталось сделать, чтобы обходы убрать.

Обозначения: 🔴 блокер (сломано сейчас) · 🟡 задача бэку · ❓ нужно решение ·
🔵 задача фронта (ждёт бэк или сделаем сами) · ✅ сделано.

Как пользоваться: взяли задачу — отметьте её в PR/комментарии и вычеркните здесь, когда
влили. Пункт закрывается тем коммитом, который его делает; про фронтовые хвосты
(убрать адаптер, включить флаг) фронт сделает сам после вашего ответа.

## 1. Блокеры — сломано на текущем `mvp`

### B1. 🔴 `created_at: str` в `EnergyDrinkSchema` → `500` на всех ответах со схемой напитка
- **Где:** `backend/schemas/energy_drink.py` (коммит `a11bb72`).
- **Что происходит:** в БД `created_at` — дата, в схеме объявлено `str` → pydantic
  `ValidationError: created_at … string_type`. Проверено: `GET /energy-drinks/`,
  `GET /energy-drinks/{id}`, `POST /energy-drinks/` отвечают `500` (запись в БД при этом
  создаётся). Каталог на фронте пустой.
- **Нужно:** `created_at: datetime` (pydantic сам сериализует в ISO 8601).
- **Фронт после исправления:** бейдж «новинка» и сортировка по свежести заработают
  (см. F1).

### B2. 🔴 `GET /energy-drinks/count` недоступен — перехватывается маршрутом `/{energy_drink_id}`
- **Где:** `backend/api/v1/energy_drink.py` (коммит `77c2fe1`): `@router.get("/count")`
  объявлен после `@router.get("/{energy_drink_id}")`.
- **Проверено:** `GET /energy-drinks/count` → `422`, `int_parsing`, `loc: ["path", "energy_drink_id"]`.
- **Нужно:** перенести `/count` выше `/{energy_drink_id}`.

## 2. Задачи бэку

### B3. 🟡 В отзывах нет связи с напитком, автора и комментария
- **Сейчас (проверено):** `GET /reviews/me` и `GET /reviews/` отдают только оценки + `id`;
  отзывы внутри `GET /energy-drinks/` — оценки без `id`. Нет `energy_drink_id`, `comment`,
  `created_at`, имени автора.
- **Что делает фронт:** отзывы собираются из вложенных в напитки, `id` у них синтетические;
  «мои отзывы», правка/удаление и лента с авторами выключены флагом `reviewAuthors`.
- **Нужно (минимум для «Моих отзывов»):** в `ReviewSchema` — `energy_drink_id`, `comment`,
  `created_at`; во вложенных в напиток отзывах — `id`. Для ленты с авторами — ещё публичное
  имя автора (B5).

### B4. 🟡 `comment` при создании отзыва молча теряется
- **Сейчас (проверено):** `ReviewCreateSchema` без `comment`; запрос с `comment` проходит
  (`201`), но комментарий не сохраняется. В `ReviewUpdateSchema` поле есть.
- **Нужно:** добавить `comment` (до 1000 символов) в `ReviewCreateSchema` — или решить, что
  комментарий ставится только через `PUT` (тогда фронт будет делать два запроса).

### B5. 🟡 Публичное имя пользователя
- **Сейчас:** у пользователя только `email`. Фронт показывает локальную часть e-mail
  (до `@`), но для чужих отзывов e-mail показывать нельзя.
- **Нужно:** `username`/`display_name` в `UserCreate`/`UserRead`/`UserUpdate` и в отзывах.

### B6. 🟡 Картинки напитков
- (а) Напиток без картинки отдаёт `200` с пустым телом (проверено на `a11bb72`); по коду
  задумано `404` — `get_image_by_id` возвращает `ImageData` с `data=None`, а не `None`.
- (б) Нет `Cache-Control`/`ETag`/`Last-Modified` — картинка (до 1 МБ) качается заново на
  каждый просмотр страницы. Пока фронт кеширует сам (`/drink-image/{id}`, 5 минут).
- (в) Оригинал отдаётся как есть. Лучше уменьшать при загрузке (≈800 px, WebP/JPEG ~80%) или
  отдавать миниатюру по `?w=`.
- (г) В схеме напитка нет признака «картинка есть» (`has_image`/`image_url`) — фронт узнаёт
  о её отсутствии только по ошибке загрузки.
- (д) `413` при превышении `MAX_ENERGY_DRINK_IMAGE_SIZE` приходит текстом
  `Content Too Large`, а не JSON `{"detail": …}`. Лимит дублируется на фронте (константа
  `MAX_IMAGE_BYTES` в `DrinkForm`) — хорошо бы отдавать его откуда-то.

### B7. 🟡 `order_by` не проверяется
- **Проверено:** `GET /energy-drinks/?order_by=bogus` → `500` (`AttributeError`), потому что
  значение уходит в `getattr(model, order_by)`.
- **Нужно:** разрешить только известные поля (whitelist/`Literal`), остальное — `422`.
  Сортировка по рейтингу в БД сейчас невозможна: такого столбца нет (см. D3).

### B8. 🟡 `get_count` грузит все строки
- `BaseRepository.get_count` делает `select(model)` и считает `len(...)`. Нужен `select(func.count())`.

### B9. 🟡 Пагинация без верхней границы
- `limit` не ограничен. Предложение: `le=100`; тогда фронту проще планировать загрузку
  (сейчас он забирает всё страницами по 100, см. `shared/api/paginate.ts`).

### B10. 🟡 `ReviewUpdateSchema`
- Оценки объявлены `Optional[float] = Field(ge=0, le=5)` без значения по умолчанию —
  в pydantic v2 это «обязательное, но может быть `null`». Частичное обновление не работает.
  Если оно нужно — `= None`. Фронт сейчас шлёт все поля.

### B11. 🟡 Время жизни токена
- `TOKEN_LIFETIME_SECONDS=86400` (24 ч), refresh нет. Это нормально, если устраивает «вход
  раз в сутки». Фронт должен брать срок cookie из токена (F3).

### B12. 🟡 Реальный IP клиента для rate limit
- Лимитер берёт IP из левого значения `X-Forwarded-For`, а запросы идут Next → бэк, поэтому
  для серверных вызовов фронта клиентом всегда выглядит контейнер фронта. Лимиты на вход,
  регистрацию и отзывы (10/мин) общие для всего сайта: достаточно десяти попыток входа в
  минуту от кого угодно, чтобы остальным отвечало `429`.
- Старый механизм (`X-Client-IP` + `INTERNAL_API_SECRET`) новый бэк не понимает.
- **Нужно решение:** как бэк узнаёт реальный IP (доверять `X-Forwarded-For` от фронта по
  общему секрету, лимитировать по e-mail/пользователю и т. п.).

### B13. 🟡 Сменить пароль SMTP
- Пароль от `energos.fun@yandex.ru` лежал в `.env.example` и остался в истории git (из файла
  убран в `dc2592e`). Его нужно сменить — считать скомпрометированным.

### B14. ❓ Лишние маршруты `/auth/{id}`
- `fastapi_users.get_users_router` публикует кроме `/me` ещё `GET`/`PATCH`/`DELETE
  /auth/{id}` (только для superuser). В `docs/api.md` они упомянуты одной строкой — нужны
  ли они или лучше убрать?

## 3. Нужны решения

### D1. ❓ Редакторская (админская) оценка
- Роль удалена (`3e3826e`), признака `from_admin` у отзыва нет, администратор оставляет
  обычный отзыв. Нужна ли в MVP «оценка редакции» отдельно от пользовательских? Если да —
  признак в `ReviewSchema` и кто может его ставить. Пока выключено флагом `adminReviews`.

### D2. ❓ Один отзыв на пользователя и напиток?
- **Проверено:** один пользователь создаёт сколько угодно отзывов на один напиток (получилось
  два). Фронт исходит из «один отзыв»: после создания открывает форму правки. Нужна
  уникальность `(user_id, energy_drink_id)` с `409` или разрешаем дубли и фронт показывает
  список своих отзывов.

### D3. ❓ Размер страницы и серверные фильтры
- Договорённость из чата: размер страницы 20. Фронт может забирать страницами по 20, но
  каталог, tier list, сравнение и карта вкусов сортируют, фильтруют и ищут по **всему**
  списку на клиенте, поэтому ему всё равно нужны все напитки сразу (рейтинг и число отзывов
  считаются на фронте из вложенных отзывов).
- Чтобы перейти на серверные сортировку/фильтры, нужно: `rating` (среднее) и `reviews_count`
  в схеме напитка и сортировка/фильтры по ним (B7), поиск по названию. Делаем в MVP или
  оставляем «грузим всё»?

### D4. ❓ Фичи вне MVP
- Избранное, эмодзи-реакции, аватарки, заявки на добавление и серверная часть достижений
  в API нет — см. таблицу флагов ниже. Что из этого входит в MVP?
