## Согласованный объём задачи

Пользователь попросил добавить смену почты и пароля в профиль. Рабочее решение: новая вкладка "Аккаунт" с двумя отдельными формами в текущем стиле, текущий пароль для подтверждения обеих операций, существующий API без изменений бэкенда.

## Что установлено по коду

- `backend/schemas/user.py`: `UserUpdate` наследует `BaseUserUpdate`, поэтому PATCH `/api/v1/auth/me` уже принимает email/password.
- `backend/services/user_manager.py`: смена email сбрасывает `is_verified` и вызывает отправку письма подтверждения. Новый пароль хешируется; правило длины — минимум 8 символов.
- Проверки текущего пароля в PATCH нет. В новых server actions нужно получить email владельца через `authApi.me(token)` и повторно вызвать `authApi.login` с этим адресом и введённым текущим паролем. Нельзя доверять email/id из скрытых полей формы.
- `authApi.updateMe` сейчас типизирован только под `{ username }`; расширить на email/password. Старый вызов смены ника должен сохраниться.
- Оба сценария используют текущую сессию. Не обещать выход со всех устройств: существующие JWT не отзываются при смене пароля.
- `ProfilePage.tsx` выводит вкладки и user.email; добавить account в TabId/TAB_IDS и исключить его из карты счётчиков наряду с appearance.
- `app/profile/page.tsx` сейчас сохраняет return-to только для appearance; добавить account.
- `VerifyEmailBanner` хранит локальное sent. При смене email нужен новый key по email, иначе кнопка повторной отправки может остаться отключённой. Его текст про письмо "при регистрации" также обобщить.

## Проверенный результат и продолжение

- Новый email становится логином, сбрасывается подтверждение, письмо доставляется в локальный Mailpit и ссылка подтверждает новый адрес.
- Новый пароль работает, старый получает 401; пробелы сохраняются. Текущая сессия остаётся активной.
- Неверный текущий пароль возвращает 401 на login. Обработчик отличает его от 401 на /me или PATCH и не разлогинивает пользователя из-за опечатки. Замечание отдельного ревью исправлено и перепроверено.
- Пароли не возвращаются в action state; минимальная длина проверяется по Unicode code points, как на бэкенде.
- Проверены две колонки на desktop, одна на 320 px, доступ к кнопке сохранения и обе темы. Основной e2e-аккаунт не изменялся.
- Главная/страница входа и API отвечают HTTP 200; каталог содержит 100 напитков.
- Account E2E запускаются только с явным `E2E_MAILPIT_URL` и только против loopback-сервисов, создавая собственные тестовые аккаунты. Временная конфигурация прогона удалена.
- Push, PR, merge и production для этой новой задачи пока не запрошены.

## Локальный стек

Основной Compose дополняется локальным `compose.v4.yml` из пользовательской папки tools. Он сохраняет отдельный том БД и использует Mailpit. Предыдущая задача проверила локальный стек логирования на `mvp`: каталог 100 напитков/8 отзывов, четыре сервиса доставляют логи; vmauth доступен только через loopback. Конфигурация и секреты остаются в игнорируемом `.env`.
